# Web Scraping & Crawling

**Bottom line up front:** the M5 Ultra Mac Studio can run a headless-browser fleet in the hundreds of contexts and an async HTTP crawler capable of five-figure req/s locally — but for *legitimate, robots/ToS-respecting* scraping, none of that local compute is what limits real-world throughput. The ceiling is set by target-site politeness limits, single-IP reputation, and macOS's default file-descriptor limit, roughly in that order, all of which bind hundreds to thousands of times below what the 36-core/512GB chassis can technically drive. This is a domain where the "enterprise-in-a-box" pitch is mostly true for the *pipeline* (headless rendering, parsing, storage) and mostly false for the *throughput ceiling* (bounded by the internet's manners, not your silicon).

## 1. What runs: headless-browser fleet and async crawler math

**Two different concurrency models show up in the sources, and they scale very differently:**

- **Multi-tab-per-browser model** — a single Playwright/Chromium browser process handles 5–10 pages/tabs before degrading, at 50–150MB per tab [Firecrawl, Playwright vs Puppeteer 2026 benchmark](https://www.firecrawl.dev/blog/playwright-vs-puppeteer). Running one browser process per CPU core (the standard way to avoid oversubscribing a shared renderer process) gives:
  - **M5 Max (18 cores):** 18 processes × 5–10 tabs = **90–180 concurrent rendered pages**, at 18 × (5–10 × 50–150MB) ≈ **4.5–27GB** — under 4–21% of its 128GB.
  - **M5 Ultra (36 cores):** 36 processes × 5–10 tabs = **180–360 concurrent rendered pages**, at ≈ **9–54GB** — under 11% of even the 256GB config that ships first (512GB configs ship later, pricing TBD).
  - **Conclusion:** for this model, CPU core count — not memory — is what sets the fleet size on both chips; memory headroom is barely touched.

- **One-browser-per-worker model** (isolated Playwright contexts, e.g. Crawlee/Playwright-test style parallelism) — baseline ≈200MB/worker regardless of page complexity [Playwright GitHub issue #38683](https://github.com/microsoft/playwright/issues/38683); confirmed independently at the same figure by [BrowserStack's Playwright parallel-test guide](https://www.browserstack.com/guide/playwright-parallel-test). Reserving ~16GB for OS/ingest overhead:
  - **M5 Max, 128GB:** (128−16)GB ÷ 200MB ≈ **~570 workers**, memory-ceiling only.
  - **M5 Ultra, 512GB:** (512−16)GB ÷ 200MB ≈ **~2,540 workers**, memory-ceiling only.
  - This is a theoretical memory ceiling, not a validated practical one: no source in evidence benchmarks Playwright concurrency against core count on M5-class silicon, so the true CPU-saturation point for this worker-per-process model is a gap (flagged below). The adjacent 16GB/20–30-instance production datapoint [(Medium/ProxyEmpire, headless Chrome at scale)](https://medium.com/@zlata_18516/headless-chrome-at-scale-cpu-ram-and-cost-optimization-strategies-caea743245c4) implies real deployments land far below the pure-memory arithmetic once CPU and target-site limits are counted — consistent with the core-bound math above, not the 200MB-only math.
  - **WebKit lever:** WebKit (Safari engine) uses ~60% less CPU than Chromium for equivalent automation on Apple Silicon [Firecrawl](https://www.firecrawl.dev/blog/playwright-vs-puppeteer), which — where the target renders correctly under WebKit — pushes the CPU-bound ceiling in the first model up correspondingly, though not every site is WebKit-compatible.

**Async HTTP crawler (no browser rendering):** asyncio 3.13 + aiohttp 3.10 measured at 12,400 req/s on a single machine, 41% over synchronous requests [dev.to benchmark](https://dev.to/johalputt/how-to-implement-async-python-with-asyncio-313-and-aiohttp-310-for-41-higher-throughput-10j1); aiohttp can sustain ~1,000 concurrent connections via `asyncio.Semaphore()`, helped by 3.10's per-host connection-pool sharding [Medium/aiohttp 1M-requests writeup](https://medium.com/@kogilaanirudh/unleashing-the-power-of-asyncio-aiohttp-making-1-million-http-requests-using-python-c0338cdf9871). A real single-machine production crawler (40 workers) sustained ~111 items/sec end-to-end (parse + dedupe + write) over a 100K-item run [Medium/scalable crawler writeup](https://medium.com/@tonywangcn/how-to-build-a-scaleable-crawler-to-crawl-million-pages-with-a-single-machine-in-just-2-hours-ab3e238d1c22) — the gap between 12,400 req/s (raw async I/O ceiling) and 111 items/sec (real crawl with parsing and politeness) is itself the headline of Section 2. For reference, compiled-language HTTP stacks show what raw local I/O ceilings look like: Rust Axum 180K–307K req/s, Go Fiber/Gin 40K–180K req/s [tech-insider.org 2026 benchmark](https://tech-insider.org/rust-vs-go-2026/) — but these are *server-side* request-handling benchmarks, not outbound-crawl benchmarks, so they bound "how fast local hardware could serve requests," not "how fast this machine can politely fetch pages from someone else's server."

## 2. Real bottleneck ordering: hardware is last, not first

For ToS-respecting scraping, the constraints bind in this order — each one caps throughput well before the M5 Ultra's compute is exercised:

1. **Politeness / target-site rate limits.** Single-node crawlers in practice run at 60–500 pages/min; distributed systems with coordinated queues reach 50,000+ req/s [Firecrawl glossary, distributed web crawling](https://www.firecrawl.dev/glossary/web-crawling-apis/what-is-distributed-web-crawling). The 4–5 order-of-magnitude gap between that and either chip's local compute ceiling exists *because* respecting robots.txt/crawl-delay and per-domain rate limits — not CPU or RAM — sets the pace against any single real target.
2. **IP diversity / reputation.** A single machine is a single (or small handful of) public IP(s). Per the Nutch FAQ (via BrightData), distributed crawling's real advantage is IP diversity, not bandwidth — bandwidth savings from distribution are minimal [BrightData](https://brightdata.com/blog/web-data/distributed-web-crawling). A single M5 Ultra can sustain a compliant crawl fine; it cannot manufacture additional legitimate IP diversity by adding cores or RAM. (Residential/ISP proxy throughput of 200Mbps–1Gbps+ is the network-external ceiling some legitimate multi-IP setups add on top [PlainProxies](https://plainproxies.com/product/unlimited-residential) — orthogonal to the Mac's own hardware.)
3. **Network/ISP uplink, not the 10GbE port.** The M5 Ultra ships with a 10 Gigabit Ethernet port (confirmed unchanged from the prior generation) [search-verified via AppleInsider / PopSci coverage of the Aug 25, 2026 announcement — direct Apple newsroom fetch was blocked in this environment, so treat as secondary-source-confirmed rather than primary]. That port is essentially decorative for scraping: crawl payloads are small text/HTML, and the binding limit is the office/home ISP uplink (typically far under 1Gbps symmetric), not the Mac's local NIC. 10GbE matters for other atlas domains (bulk video/data transfer on a fast LAN); it is not what a scraping workload will ever saturate.
4. **File descriptors, before CPU/RAM.** macOS's default FD limit is 256, tunable up to a max of 12,288 [wilsonmar.github.io macOS limits reference](https://wilsonmar.github.io/maximum-limits/). The aiohttp 1,000-concurrent-connection pattern above requires an explicit FD-limit raise to even start — at the 256 default it fails or throttles hard before a single CPU core or GB of RAM is stressed. Headless-browser fleets compound this: each browser process/context opens its own sockets and IPC pipes on top of the crawler's own connections, so FD headroom, not memory or cores, is usually the first hardware-adjacent wall hit when scaling either concurrency model above.
5. **Only then, hardware.** Once politeness, IP diversity, uplink, and FD limits are addressed, CPU cores and memory are what's left — and as Section 1 shows, both chips have far more of both than a compliant single-target crawl can use. The M5 Ultra's extra 18 cores and 384–448GB of memory over the M5 Max buy headroom for *running many independent low-rate crawls/parsers/browser-fleets in parallel across many different targets*, not for going faster against any one target.

**Net:** for this domain specifically, the jump from M5 Max to M5 Ultra is the least load-bearing hardware decision in the atlas — the binding constraints sit outside the chassis entirely.

## 3. Ingest/storage path: crawl output → DuckDB/Parquet on the SSD

DuckDB writes Parquet 4–15x faster than SQLite, and Parquet export beats writing into an in-memory Pandas DataFrame [Galaxy DuckDB-vs-SQLite benchmark](https://www.getgalaxy.io/learn/glossary/duckdb-vs-sqlite-benchmarks). DuckDB 1.3.0+ added multithreaded Parquet export and rowgroup merging, scaling well under ~10GB per file/table but degrading relative to Arrow beyond that [MotherDuck, DuckDB 1.3 announcement](https://motherduck.com/blog/announcing-duckdb-13-on-motherduck-cdw/) — so the practical ingest pattern is **partitioned Parquet writes** (batch/shard by crawl run or time window, each under ~10GB) rather than one continuously-growing table, to stay inside DuckDB's efficient zone.

**Rate math against the SSD ceiling:** at the sourced real-world single-machine rate of ~111 items/sec [Medium scalable-crawler writeup](https://medium.com/@tonywangcn/how-to-build-a-scaleable-crawler-to-crawl-million-pages-with-a-single-machine-in-just-2-hours-ab3e238d1c22), even a generous 5KB average parsed/stored record works out to ≈555KB/s ≈ 48GB/day. Against the M5 Ultra's 16TB SSD, that's **~330 days of continuous ingest headroom** before storage capacity is the limiter — and against the M5 Max's smaller 8TB ceiling (per the verified hardware envelope), still ~165 days. **Storage capacity is a non-issue for scraping specifically** at any throughput this domain's politeness limits will actually allow; it would only become relevant if the "16TB SSD" were being filled by something else in the atlas (bulk media, video) running alongside the crawl.

## 4. macOS-specific constraints and ARM64 tooling maturity

- **File descriptors (see §2.4):** default 256, raisable to a max of 12,288 [wilsonmar.github.io](https://wilsonmar.github.io/maximum-limits/) — this is a required `ulimit`/`launchctl` step before running high-concurrency async crawlers or large browser-context fleets, not an optional tuning knob. It is a hard macOS-wide ceiling independent of chip.
- **macOS network stack tuning** (ephemeral port range, kernel-level socket ceilings) beyond the FD limit above is **not covered in the evidence base** — flagged as an open gap rather than asserted from memory.
- **ARM64 Python:** native ARM64 Python outperforms x86_64-under-Rosetta-2 by 1.78–1.98x; the Rosetta 2 penalty is typically 20–30% and can exceed 50% for CPU-heavy workloads [pushtoprod Apple Silicon Python benchmark](https://pushtoprod.substack.com/p/making-python-2x-faster-on-apple-silicon) — running scraping stacks under an x86_64 Python install (common if inherited from an Intel-era project) silently gives away up to half the chip's throughput.
- **curl-cffi and Scrapy:** curl-cffi ships native ARM64 wheels for macOS, and Scrapy's earlier ARM64 issues are resolved in recent versions [PyPI curl-cffi](https://pypi.org/project/curl-cffi/).
- **Playwright/Chromium/WebKit:** Playwright's browser binaries for both Chromium and WebKit are now built natively for Apple Silicon and run without Rosetta — but this needs verifying per-install, since some install/config paths have historically defaulted to downloading the x86_64 Chromium build even on M-series Macs, silently forcing Rosetta translation [Playwright GitHub issues #19602](https://github.com/microsoft/playwright/issues/19602), [#19586](https://github.com/microsoft/playwright/issues/19586). Given the 1.78–1.98x native/Rosetta gap above, confirming `PLAYWRIGHT_BROWSERS_PATH`/arch on first setup is a real, easy-to-miss performance trap on this hardware.
- **Ecosystem direction:** macOS Tahoe (Sept 15, 2025) is the last Intel-compatible macOS version; everything after is ARM64-only [Wikipedia, macOS Tahoe](https://en.wikipedia.org/wiki/MacOS_Tahoe), reinforcing that ARM64-native tooling is now the only forward-supported path, not an optimization.

## 5. Hard ceilings, nearest server-class equivalent, and where the pitch holds vs. breaks

- **Hard ceiling for this machine, this domain:** somewhere in the low hundreds of concurrent rendered pages (CPU-bound, Section 1) or low-thousands of lightweight async connections (FD/memory-bound once `ulimit` is raised) — and in practice throttled far below either by per-domain politeness (60–500 pages/min/domain-class figures) long before those local ceilings are approached.
- **Nearest server-class equivalent:** not a bigger single box. The sourced comparison is single-node (60–500 pages/min) vs. **distributed** crawlers with coordinated work queues across many machines/IPs (50,000+ req/s) [Firecrawl glossary](https://www.firecrawl.dev/glossary/web-crawling-apis/what-is-distributed-web-crawling). A handful of small, geographically/IP-diverse cloud VMs beats one M5 Ultra on real-world compliant throughput — not through more cores or RAM per node, but because IP diversity is the scarce resource this domain actually prices in [BrightData/Nutch FAQ](https://brightdata.com/blog/web-data/distributed-web-crawling).
- **Where "enterprise-in-a-box" holds:** the *pipeline* — rendering hundreds of pages concurrently, running the parse/dedupe/store loop, and landing everything in DuckDB/Parquet on fast local NVMe with ~330 days of ingest headroom before storage is even a conversation. For in-house crawling of your own properties, QA/regression browser fleets, or low-to-moderate-volume public-data collection against a modest number of domains, the M5 Ultra (or even the M5 Max) is genuinely oversized relative to what's needed — which is the point: it holds up as a capable single-node pipeline machine.
- **Where it breaks:** anything that needs IP diversity, or throughput against rate-limited third-party sites beyond what a single compliant IP can sustain. No amount of additional cores, memory, or the 10GbE port changes that calculus. The Ultra-over-Max premium buys parallel *breadth* (more independent low-rate jobs against more distinct targets at once) far more than it buys *speed* against any one target.

## Confidence & gaps

**High confidence:** headless-browser per-tab/per-worker memory figures (multiple corroborating sources); macOS FD limit values; native-ARM64-vs-Rosetta 2 performance gap; DuckDB/Parquet vs. SQLite relative performance; distributed vs. single-node throughput and IP-diversity-over-bandwidth framing (BrightData/Nutch).

**Medium confidence:** the 16GB/20–30-instance production datapoint (single source, hardware unspecified, likely conflates CPU and memory limits — used only qualitatively above, not scaled linearly); Botify/typical-service req/s ranges; residential proxy throughput figures (vendor-sourced).

**Gaps / open questions:**
1. No source in evidence benchmarks Playwright/Chromium concurrency directly against M5 Max/Ultra core counts — the "~570 / ~2,540 worker" memory-ceiling math in §1 is arithmetic from a generic 200MB/worker figure, not a tested ceiling on this silicon; the true CPU-saturation point for the one-browser-per-worker model is estimated by analogy (§1's multi-tab model), not measured.
2. macOS network-stack limits beyond the FD ceiling (ephemeral port range, kernel socket ceilings) are not covered by any source in the fact file and were not found in supplemental search — flagged rather than asserted.
3. The 10GbE port claim was confirmed via search-engine snippets referencing AppleInsider/PopSci coverage of the Aug 25, 2026 Apple announcement; direct fetch of apple.com and those secondary sources was blocked by this environment's egress proxy, so it is secondary-source-confirmed, not independently verified against the primary press release in this session.
4. Real-world sustainable req/s against a *specific* target site (as opposed to generic "single-node" and "distributed" figures) depends entirely on that target's own rate-limit policy, which is out of scope for a hardware-capability estimate and necessarily excluded here.
